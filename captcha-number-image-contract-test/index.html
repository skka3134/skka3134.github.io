A captcha number image contract test for payloads, polling, and expiry

2026-11-27

A captcha number image integration has three separate contracts: the bytes you upload, the asynchronous job you poll, and the answer you put back into the form. A demo can exercise all three once and still hide expensive failures. The useful tests are the ones that pin down what happens when each contract is slightly wrong.

Test the request before sending a live image

The API reference defines image_data as a required array. Each entry can be raw base64 or a data URI. That array matters: a shorter mathematical-captcha example shows a bare base64 string, while the API quickstart and request-body documentation use a one-element array. Build the client against the documented array shape and keep a test that rejects accidental changes.

Start with a local request-building test. It should not contact the service:

import base64
from pathlib import Path

URL = "https://fuckcaptcha.top/v1/recognition/textcaptcha"


def build_submit(image_path, key):
    image = Path(image_path).read_bytes()
    encoded = base64.b64encode(image).decode("ascii")
    headers = {
        "Authorization": f"Basic {key}",
        "Content-Type": "application/json",
    }
    payload = {"image_data": [encoded]}
    return URL, headers, payload, image


def test_submit_shape():
    key = "nsk_test_key"
    url, headers, payload, original = build_submit("fixture.png", key)

    assert url.endswith("/v1/recognition/textcaptcha")
    assert headers["Authorization"] == "Basic nsk_test_key"
    assert isinstance(payload["image_data"], list)
    assert len(payload["image_data"]) == 1
    assert base64.b64decode(payload["image_data"][0]) == original

This catches two easy mistakes. First, the key goes directly after Basic; it is not base64-encoded. Second, decoding image_data[0] must reproduce the original file byte for byte. A screenshot that is blank, transparent, or from the wrong frame can still pass a JSON-schema test, so keep the original fixture beside the test and inspect it when image-extraction code changes.

Keep cookies out of the recognition test

The mathematical-captcha guide says recognition needs only the image, not the target site's session. Your client should put the answer back into its own browser or scraper session, but the recognition request itself does not need those cookies. A test that compares the outgoing headers against an exact allowlist will catch accidental session leakage.

Poll one job ID, not a new job every cycle

Submitting an image returns a job ID, not the answer:

{"data":"nsj_example_job"}

The result comes from a GET to the same recognition endpoint with that ID. While work is pending, the response contains error: 14. That means "ask again", not "submit again".

import time
import requests

URL = "https://fuckcaptcha.top/v1/recognition/textcaptcha"


def poll_answer(job_id, key, timeout=170):
    headers = {"Authorization": f"Basic {key}"}
    deadline = time.monotonic() + timeout
    delay = 0.5

    while time.monotonic() < deadline:
        response = requests.get(
            URL,
            headers=headers,
            params={"id": job_id},
            timeout=10,
        )
        body = response.json()

        if body.get("error") == 14:
            time.sleep(delay)
            delay = min(delay * 1.2, 3)
            continue

        if "error" in body:
            raise RuntimeError(body)

        values = body.get("data")
        if not isinstance(values, list) or not values:
            raise ValueError(f"Unexpected result: {body!r}")
        if not all(isinstance(value, str) for value in values):
            raise ValueError(f"Unexpected answer type: {body!r}")

        return body

    raise TimeoutError(job_id)

The client-side deadline is deliberately shorter than the service's three-minute recognition-job lifetime. The client can report a timeout while the job ID is still valid instead of discovering expiry at the same moment it stops waiting.

Make the state transitions explicit

Use a fake transport for these cases rather than repeatedly calling the live endpoint:

  • A submit response containing error is a rejected request. Bad parameters, no credit, or no upstream capacity do not charge the client.
  • A successful submit followed by error: 14 means the same job is still running. Assert that no second POST occurs.
  • A successful submit followed by another error means the accepted job failed or timed out. That attempt was already charged and is not refunded.
  • error: 16 means there is not enough credit. Do not turn it into a tight retry loop; the documented quota resets daily at midnight Beijing time.
  • A local timeout should raise with the job ID attached so the failure can be traced without guessing which image was involved.

Nearly all API errors use HTTP 200. response.ok therefore cannot be the success condition; the JSON error field is the contract.

Unwrap the answer instead of assuming its type

The text-captcha example in the API reference returns:

{"data":["H7K5"],"metadata":{}}

So the integration needs to unwrap data and handle its list of strings. Writing result["data"] directly into a form field can produce a string representation of a list rather than the recognized text.

Add a second fixture for a data URI and verify that both input forms produce the same request structure after normalization. Keep malformed-result fixtures too: an empty list, a bare string where a list is expected, and an error body with HTTP 200. These tests cost nothing and protect the code that fills the form.

Keep the live smoke test small

Once the local contract tests pass, use one known image for a live check. The current API price list puts text-captcha image recognition at one credit per accepted call, and polling does not create another recognition charge. That makes a single smoke test reasonable; running every fixture against production is not.

For the deployed check, captcha number image exposes the text-captcha recognition path, while the API reference documents the request fields, job lifetime, result shapes, and error codes. The mathematical-captcha guide is useful for confirming that arithmetic images use the same textcaptcha endpoint rather than a separate type.

The final assertion is simple: one image goes in, one job ID comes back, that ID is polled until completion or client timeout, and one recognized string goes into the form. Everything else is a failure mode worth testing before it reaches a paid request.
